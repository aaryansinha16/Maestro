## 1. Executive summary

Maestro is a **coherent, well-engineered, fully single-user system that is
mid-deployment to Railway** — materially further along than its own docs claim.
Engineering discipline is high: strict TypeScript, no `any`, Zod at every
boundary, `execa` array-args (no shell strings), 141 passing tests.

The gap is **not "is it built" — it's "has it run."** The autonomous loop is
implemented end-to-end but essentially unproven: one project registered,
scheduling still off, four sessions ever executed (two failed). Before trusting
autonomy there is a cluster of real correctness bugs to fix; before exposing it
publicly there is a finite hardening checklist; and going global multi-user is a
deliberate re-platform, now unblocked by the "bring your own Claude
subscription" decision.

## 3. Engine correctness cluster — fix before trusting autonomy

These undermine the safety guarantees the product markets. Tests pass because
they don't exercise these edge paths. Ordered by severity.

> **✅ Fixed 2026-07-17 (branch `fix/audit-engine-correctness`):** ENG-01, ENG-02,
> ENG-03, ENG-05 — each with new tests — plus a deterministic session-ordering
> fix (`rowid` tiebreaker) that also resolves the long-standing auto-pause test
> flake. Full suite 147/147, typecheck + lint clean. **ENG-04** is a pending
> product decision (manual-trigger override UX). ENG-06…ENG-18 remain open.

| **ENG-01** | High | **Auto-pause never auto-clears.** `maybeClearAutoPauseOnManualSuccess` is never called, so a successful manual run does not un-pause a project (contradicts the module's own docstring). rewrite.

|---|---|---|---|

## 7. Global reach via self-hosting (compliant, subscription-only)

**Product decision (made):** Maestro will be usable by everyone, but as
**self-hosted software** — each user runs their own instance and connects their
**own** Claude Pro/Max subscription. Two shapes are in scope, both compliant
("their creds, their box"):

1. A user runs Maestro on their own machine / VPS with their own `claude` login.
2. A user deploys their own instance to their own cloud (one-click template).

**Why not a hosted SaaS.** Anthropic's Claude Code policy prohibits third-party
developers from "routing requests through Free, Pro, or Max plan credentials
**on behalf of their users**." The line is not subscription-vs-API — it is
*whose server the credentials run on*:

| Model | Whose creds / whose server | Compliant |
|---|---|---|
| User runs their own instance + own login | theirs / theirs | ✅ |
| User deploys their own instance to their cloud | theirs / theirs | ✅ |
| We host it; users paste subscription tokens into our servers | theirs / **ours** | ❌ |

_Caveat: this rests on a reading of Anthropic's published "Legal and compliance"
policy for Claude Code, not legal advice — confirm the live ToS before
committing, and contact Anthropic sales if a hosted shape is ever wanted._

**Key consequence — this is distribution + DX, NOT a re-platform.** The current
deliberately single-tenant architecture (ADR-012, ADR-020) is *already correct*
for self-hosting: one instance = one owner. The heavy multi-tenant blockers from
a SaaS design **drop out** — no tenancy columns, no per-user credential vault on
shared infra, no multi-tenant sandbox, no distributed queue, no Postgres.

### In scope — make it a great self-hostable product
| ID | Item |
|---|---|
| **SH-01** | **One-click / templated deploy.** Railway template + `docker run` one-liner + a short "deploy your own" guide. The image already exists; package it so a stranger can launch in minutes. |
| **SH-02** | **Headless BYO-auth via the user's own token.** Support `CLAUDE_CODE_OAUTH_TOKEN` (from the user's own `claude setup-token`, a ~1-year token) so a user authenticates a headless instance by pasting *their own* token as an env var — removing the fragile interactive `railway shell` + `claude /login` bootstrap (ADR-025). Compliant: their token, their box. |
| **SH-03** | **First-run onboarding.** Guided setup (identity, GitHub token, auth creds); the Claude-health banner already exists — add a setup checklist and use the existing AddProject wizard as the front door. |
| **SH-04** | **Harden for public exposure** (cross-refs PROD-01/03/05): auth fail-closed in production, security headers, login rate-limiting — self-hosters will expose instances to the internet. |
| **SH-05** | **Packaging & distribution.** Versioned Docker image on a registry, pinned `claude` CLI compatibility, release notes, clear docs; decide licensing / open-source. |

### Explicitly OUT of scope (would only matter for a hosted SaaS)
Tenancy columns, per-user credential vaulting on shared infra, a multi-tenant
per-session sandbox for untrusted strangers, distributed job queue, Postgres +
object storage, per-tenant billing/RBAC. Revisit only if the product ever
pursues an Anthropic commercial agreement for a hosted offering.

_Note: MU-01 (sandbox) doesn't vanish entirely — it downgrades from "critical
multi-tenant blocker" to normal single-owner hardening (PROD-03), since a
self-hoster again runs only their own repos._

## 8. Security findings (consolidated, most→least severe)

| ID | Finding |
|---|---|
| **SEC-01** | Untrusted agent runs with same-user access to all secrets & tenants (`bypassPermissions` + `Bash`, no OS sandbox). Prompt injection via `.maestro/`/repo content is live even single-user. → MU-01/PROD-03. |
| **SEC-02** | No network egress control; agent `Bash` and quality-gate scripts run arbitrary code with full FS access. |
| **SEC-03** | Auth fail-open + weak single credential, no lockout/rate-limit → PROD-01/PROD-05. |
| **SEC-04** | Shared GitHub PAT over-scoped (read/write to *all* the developer's repos) → MU-04. |
| **SEC-05** | Backups co-located with data (DR risk) → PROD-02. |
| **SEC-06** | No CSRF protection / security headers; risky if `MAESTRO_CORS_ORIGIN` is set loosely → PROD-05. |
| **✓** | **Positives worth crediting:** non-root via gosu; static-file path-traversal contained; `execa` array-args never shell strings; PR-feedback author-allowlisted; Hono basicAuth constant-time compare; all DB rows Zod-validated on read. |
